# L2 技术设计：停住的工作由负责人继续推进

版本：v0.1，2026-10-06；状态：Draft。依据：[L1 v0.1](product.md) 的 S1.A1、S2.A1、S3.A1、S4.A1、S5.A1，以及 [Issue #20](https://github.com/xforce-io/atelier/issues/20)。

机制出处见本轮 keel-how：`runs::stopped` / `notify_failure`、`recovery::ensure`、`retry` 对已受理 execute/rework 的拒绝、`rework::arrange` / `claimable` 的 `max_reworks` 比较、`disposition::valid_for_stop`。

## 1. 设计依据与技术目标

落实 L1 v0.1。普通停止回到团队负责人的一条工作消息。同一种空停止不派生下一轮。凭据缺失、授权撤销和连接失败仍走现有恢复事项。不改提供方超时，不自动重试单次模型请求，不新增工具或错误码。

## 2. 现状与改动范围

`runs::stopped` 在没有有效 `message_respond` 时把投递写成 blocked，并调用 `notify_failure`。`recovery::ensure` 在接收者是数字员工团队负责人、且投递为 blocked 或 uncertain 时，给本人创建 `kind=recovery` 并返回 true，于是不再给负责人发消息。

成员执行的接收者不是负责人，所以成员停止今天已经会发失败消息。卡住发生在负责人自己的投递：`ensure` 改走本人的 retry、wait、cancel。

改动留在 `notify_failure`、`recovery::ensure` 的调用条件、`require_retry_choice`，以及返工安排和领取时对旧默认上限的比较。不改 `mailbox retry` 对已受理代码执行的拒绝。不改 `classify` 的事实分类。

## 3. 总体架构与关键路径

资源已核对且投递变为 blocked 或 uncertain 时：

1. 停止事实属于凭据缺失、授权撤销或连接失败：仍调用 `recovery::ensure`。已有未结束事项时不重复创建。不另给负责人自动排一轮。
2. 其它停止：不创建恢复事项。若停止的是执行或返工，且留下了新事实，则给负责人投递一条 `failure` 工作消息。事件键按该投递与停止原因固定，同一事实只投递一次。
3. 若停止的是负责人自己的一轮，且本轮没有新事实，停止原因与该投递已有原因相同：不投递新的工作消息，不增加 Run。

服务启动时，若任务上仍有未结束的普通恢复事项，最新的执行或返工已停止并留下普通事实，且负责人没有待处理的工作消息，则补投一条 `failure`。事件键是 `ordinary-continue:{投递}`，同一投递只补一次。凭据、授权撤销、连接失败和尚未核对的事项不走这条补投。

## 4. 数据与状态契约

不新增表，不新增决策种类。恢复事项的存储形状不变。

新事实指本轮在核心里留下的改变任务的记录：安排、返工、交接、产出、检查、正式阻塞、待决定事项，或与该投递已记录原因不同的停止原因。`task_read` 与 `decision_read` 不产生这些记录，不算新事实。

`Contract.max_reworks` 仍保存。安排和领取时，值为旧默认 2 视为未收紧，不因此拒绝。承接前收紧到更小的正整数时仍拒绝超出的安排和领取。`max_runs` 默认 20、`max_messages` 默认 100 的比较不变。已打开的普通恢复事项不删除、不改答。`require_retry_choice` 不再因这种普通事项挡住后续工作消息。凭据、授权撤销和连接失败的事项仍挡住「必须先选择 retry」。

## 5. 接口与协作契约

不新增 CLI，不新增成员工具。工作消息继续使用现有 `failure` 种类，正文仍带 `runId`、`deliveryId`、`reason`。恢复事项的 list/show 结构不变。已受理 execute/rework 的原样重试仍返回现有冲突错误，投递状态不改。

## 6. 运行与保障机制

自动续接只发生在新的成员停止事实，或启动时补上一条尚未投递的同类事实。负责人自己的空停止不调用模型。重复检测靠事件键，不靠新增计数器。运行额度仍在领取时消费。未知资源保持 uncertain，不在未核对时投递续接消息。

## 7. 迁移、发布与回滚

不提升 `user_version`，不改写已有决策 JSON。旧任务上的 `max_reworks=2` 由代码按未收紧处理，不回写数据库。回滚到旧二进制后，这些任务会重新受 2 次上限约束；已发出的工作消息保留。

## 9. 技术风险与开放问题

已有普通恢复事项留在库里，查询仍能看到。它们不再挡住新的工作消息。不在本次把它们标成取消。

运行次数 20 仍可能在长任务上耗尽。本次不放宽，也不把耗尽改成自动重试。
